
# TRACE 产品与工程整改计划
## 基于 Spec Kit 的分阶段开发、测试、去冗余与交付

**文档状态：团队讨论稿，尚未启动实施。**

本计划适用于“codex欧莱雅持续更新版”中的 TRACE / AccessibleBeautyAgent 项目。目标是将产品需求、工程实现、测试证据、缺陷修复和结构维护统一到 Spec Kit 工作流中，逐阶段交付可运行、可理解、可验证、可回退的版本。

---

## 一、整改目标与产品边界

### 1. 整改要解决的问题

老师提出“要按照 Spec Kit 的结构化方式去写”，应落实为以下工程要求：

- 写代码前，先明确用户需要什么、什么情况算正确。
- 对状态、权限、接口和异常行为形成统一约定。
- 每项修改有需求依据、任务编号和验收方法。
- 每个 bug 能复现、定位、修复并通过回归验证。
- 每阶段同步清理被替换的逻辑，避免新旧实现不断叠加。
- 队友能够根据文档找到修改位置，理解影响范围并复核结果。

Spec Kit 提供组织这些工作的流程；真正减少 bug，还需要一致的业务规则、清晰的模块边界和有效的测试。

### 2. 产品目标

TRACE 面向盲人和低视力用户的美妆与审美表达需求，提供以语音为主、文字与视觉能力辅助的交互体验。

核心使用过程为：

> 表达需求 → 澄清场景和偏好 → 选择可选方案 → 按步骤执行或自由交流 → 查看事实性总结 → 自主决定是否保存 → 经确认后用于下一次体验。

需要支持：

- 自由交流，不强迫用户进入化妆流程。
- 根据场景、时间、工具、偏好和避讳提供建议。
- 一次一个可操作步骤的教学。
- 暂停、继续、重复、解释、跳过和提前结束。
- 可选的本地视觉观察。
- Full Look 六领域建议：发型、妆容、护肤、穿搭、配饰、香氛。
- 标签读取及有来源的产品比较。
- 独立使用日志功能，不要求先完成课程。
- 经用户确认的摘要、日志与偏好管理。
- 键盘、文字和读屏可完成核心任务。

### 3. 本轮边界

| 项目 | 本轮决定 |
|---|---|
| 交付方向 | 面向小范围真实试用，先形成工程候选版 |
| 平台 | Mac、Windows 浏览器 |
| 语音 | 保留按钮与起止词交互，不扩展为全双工语音 |
| 联网 | 文字可调用远程服务；标签图片单独取得外传授权 |
| 本地能力 | 语音识别与现有本地视觉测量继续保留 |
| 视觉范围 | 画面质量、定位、颜色差异和不确定性表达 |
| 视觉研究 | 真实妆效判断另建研究规格，不混入本轮验收 |
| 个人记忆 | 摘要、日志、偏好分别展示、修改、确认后保存 |
| 当前验证资源 | 团队自测；专业审核和目标用户测试作为后续试用条件 |
| 技术路线 | 延续 React、TypeScript、FastAPI、SQLite 和本地语音，渐进改造 |
| 暂不扩展 | 美貌评分、医疗判断、心理诊断、自动购买、未经验证的硬件能力 |

### 4. 两个交付里程碑

**工程候选版**

自动化检查、团队双平台设备检查、权限与数据流程验证完成；限制和未验证项有明确记录。

**真实试用版**

在工程候选版基础上，试用课程经过专业审核，盲人或低视力目标用户完成关键任务验证。

只有团队自测时，不将产品标记为已经通过真实用户验证。

## 二、现状核查与实施原则

### 1. 实施前必须重新建立基线

历史检查、旧测试报告和白皮书中的目标不等于当前能力。阶段 0 重新记录：

- 当前代码版本、工作区状态及已有 Spec Kit 文件。
- 实际启动入口、端口、运行环境和模型配置。
- 核心模块、状态来源、数据库及外部服务。
- 实际通过、失败、未运行和受阻的测试。
- 已实现、部分实现、演示、研究中和尚未实现的功能。
- 当前资料与实际代码之间的冲突。

白皮书用于确认产品意图，代码和运行证据用于确认实现情况。此前读取的 PPT 为比赛模板，不作为完整产品方案或实现证据。

### 2. 当前需要重点核查的结构

既有检查发现：

- 前端入口同时协调会话、语音、相机和请求生命周期。
- 后端存在旧流程字段与教学计划之间的同步。
- 多个交互入口需要共同遵守步骤推进、授权与保存规则。

这些是结构审查对象，不能仅凭静态观察认定为已复现 bug。

### 3. 渐进改造原则

- 每阶段保持主要使用流程可运行。
- 优先修复状态、权限、数据一致性问题，再扩展表现层。
- 先保护正确行为，再迁移实现和删除旧路径。
- 已知错误行为按规格纠正，不用测试将错误固化。
- 数据和接口变化必须有迁移及回退方案。
- 外部服务或人工审核受阻时，可以继续独立任务，但不能将受阻项目标为通过。

## 三、Spec Kit 的组织方式与质量关卡

### 1. 工作流程

每阶段采用：

`constitution → specify → clarify → plan → checklist → tasks → analyze → implement → converge`

各环节职责：

| 环节 | 本项目中的用途 |
|---|---|
| constitution | 约定不可随意破坏的产品与工程原则 |
| specify | 明确用户故事、范围、行为及验收条件 |
| clarify | 解决状态、权限、异常和产品意图歧义 |
| plan | 明确模块职责、接口、数据流、迁移与去冗余方案 |
| checklist | 检查需求是否完整、明确、一致 |
| tasks | 拆成有依赖关系、可执行、可验证的任务 |
| analyze | 检查规格、方案和任务是否冲突或遗漏 |
| implement | 按批准范围实施当阶段任务 |
| converge | 对照规格检查缺口，补充后续任务并继续验证 |

具体调用形式以正式实施时选定的 Spec Kit 版本及 Codex 集成为准。

`converge` 不代替测试、设备验证和人工评审，也不会自动删除冗余代码。[官方流程说明](https://github.github.io/spec-kit/reference/agentic-sdd.html)

### 2. 计划目录

正式实施时，在项目 Git 根目录建立或整理：

```text
.specify/
  memory/constitution.md
  [所选版本生成的其他资源]

specs/
  001-runtime-baseline/
  002-session-control/
  003-dialogue-knowledge/
  004-voice-interaction/
  005-local-vision/
  006-styling-reading/
  007-confirmed-memory/
  008-accessible-release/

docs/quality/
  baseline.md
  capability-matrix.md
  bugs.md
  traceability.md
  architecture-cleanup.md
  evidence/

AccessibleBeautyAgent/
```

总体路线先确定；当前阶段详细展开，后续阶段在开始前依据前序结果更新。避免一次写出大量与实现迅速脱节的细节。

### 3. 每阶段文档

| 文档 | 必须包含的内容 |
|---|---|
| `spec.md` | 用户故事、范围、必须保留和允许改变的行为、异常及验收场景 |
| `plan.md` | 模块职责、数据流、接口影响、保留与删除的实现、迁移和回退 |
| `tasks.md` | 测试保护、实现、调用方迁移、旧代码移除和验证任务 |
| `checklists/requirements.md` | 需求质量检查 |
| `verification.md` | 测试结果、环境、版本、证据、未验证项和阶段结论 |
| `contracts/` | 涉及变化的 API、事件和错误契约 |
| `data-model.md` | 涉及变化的数据结构、生命周期和迁移 |
| `research.md` | 尚需调查的技术问题及结论，按需建立 |

架构决定写入对应阶段的方案，共用结构整改清单只记录状态并引用方案，避免重复维护多份完整说明。

### 4. 阶段启动和完成条件

- 影响核心行为的歧义未解决，不实施相应任务。
- 规格、设计和任务存在重大冲突，先修正文档。
- 行为发生变化，先更新需求及验收，再修改实现。
- 需求评审通过、代码完成、测试通过分别记录。
- 自定义评审清单由实际评审者确认，实施者不能静默代为批准。
- 发现遗漏后追加任务，实施并验证后才能关闭。

## 四、项目原则：功能正确与去冗余共同约束

### 1. 产品与数据原则

1. 后端决定业务进度，前端展示权威状态快照。
2. 闲聊、重复、解释和否定表达不自动推进步骤。
3. 明确推进操作具备幂等性，重试不重复执行。
4. 暂停保留进度；恢复会话不恢复媒体授权。
5. 相机预览、本地分析、持续观察和远程上传分别管理授权。
6. 摘要、日志、偏好分别经用户确认后保存。
7. 课程、产品、观察结果和模型输出保留来源及可信程度。
8. 用户能够用文字、键盘和读屏完成关键任务。
9. 交付证据绑定代码、配置、知识库和运行环境版本。

### 2. 去冗余与可维护性原则

| 原则 | 执行要求 |
|---|---|
| 业务规则有唯一归属 | 步骤推进、暂停、结束、授权和保存不在多个入口分别实现 |
| 状态有明确权威来源 | 派生状态尽量计算得到；确需缓存时定义失效机制 |
| 兼容入口只负责转换 | 旧接口转发到统一服务，不保留另一套业务判断 |
| 依赖方向清晰 | 页面→交互协调→API；后端路由→业务服务→存储或供应商适配 |
| 按职责拆分 | 拆分要减少隐式耦合，不只是把大文件切碎 |
| 适度抽象 | 有稳定、同语义的重复才抽取；领域差异不强行统一 |
| 新实现交代旧实现去向 | 明确删除、迁移或兼容，不长期并行维护 |
| 文档有权威来源 | 启动、配置、业务规则各有归属，其他文档引用 |
| 不以代码量论成效 | 关注修改同一规则需要触及多少位置，以及验证是否更容易 |

不为本轮改造额外引入通用工作流引擎、复杂继承体系或没有现实用途的扩展层。

### 3. 旧实现退出机制

每个替换任务明确：

- 被替换实现及真实调用方。
- 新实现的职责和兼容范围。
- 调用方迁移顺序。
- 删除旧代码的条件与测试。
- 暂时保留的原因、负责人和最迟清理阶段。

删除旧实现必须进入任务清单。判断无用代码时同时核查静态引用、动态加载、启动脚本、配置、测试、演示和打包入口。

不能以“可能以后有用”为唯一保留理由。

## 五、分阶段修改与交付

### 阶段 0：建立 Spec Kit、产品与工程基线

**目的**

让后续开发有统一的需求来源、工程约束和问题清单。

**工作**

- 核查当前 Git 与工作区状态，建立可回退基线。
- 固定 Spec Kit 版本，审查初始化文件变更。
- 建立项目原则、能力矩阵及需求追踪规则。
- 绘制主要模块、状态变化与数据流。
- 区分产品目标、当前行为和已验证能力。
- 建立“保留、合并、替换、删除、待核实”结构清单。
- 标识历史文档，避免将旧说明继续作为当前操作依据。

**交付**

规范目录、能力矩阵、基线报告、架构说明、缺陷清单、结构整改清单。

**完成条件**

核心操作都能对应实际入口、规则和存储位置；疑似风险与已复现缺陷分开记录；后续阶段依赖明确。

---

### 阶段 1：运行环境与测试基线
**规格：001-runtime-baseline**

**功能与工程工作**

- 以 Python 3.12 为环境基线，验证并固定兼容的 Node 与平台依赖。
- 明确语音、视觉模型下载、版本、校验和缺失处理。
- 统一安装、启动、停止、健康检查与环境诊断。
- 测试数据库、端口和配置与日常使用隔离。
- 执行后端测试、前端测试、构建及知识库检查。
- 覆盖中文路径、空格路径、移动目录、端口占用和重复启动。

**去冗余**

收敛重复启动脚本、配置默认值、端口说明和环境变量解释；保留明确的平台差异。

**交付**

可运行基线、双平台安装说明、环境检查结果、测试基线与缺陷列表。

**完成条件**

干净环境可按说明启动；启动器只管理自身服务；失败提示可操作。原有失败测试被如实记录，不通过放宽断言制造通过。

---

### 阶段 2：会话状态、步骤与取消机制
**规格：002-session-control**

**功能与工程工作**

- 明确会话、教学计划、语音通话和授权的状态边界。
- 统一开始、下一步、跳过、暂停、恢复、结束命令。
- 旧路由与新路由调用同一业务服务。
- 逐步将旧进度字段改为兼容输出，避免双向同步。
- 使用事件标识、预期步骤和必要版本校验处理重复及过期操作。
- 前端按会话、请求、语音和相机职责拆分协调逻辑。
- 区分停止播报、丢弃录音、暂停课程和结束会话。
- 网络断开后查询已提交结果，不能通过重发新事件重复执行。
- 提前关闭绕过确认的自动个人摘要保存入口，阶段 7 再补齐完整保存体验。

**重点场景**

重复不会推进；“还没完成”不被当作完成；重复进入总结不重建计划；跳过与完成有区别；提前结束不伪造全部完成；刷新不恢复媒体授权。

**去冗余**

收敛重复状态、推进逻辑、错误处理和过期响应处理。页面不再自行维护另一套业务规则。

**交付与完成条件**

状态图、命令契约、会话实现及竞争场景测试。按钮、文字、语音执行同一操作结果一致；重试不多走一步，迟到响应不覆盖新状态。

---

### 阶段 3：对话、知识库与可执行教学
**规格：003-dialogue-knowledge**

**功能与工程工作**

- 支持自由交流并保持当前进度。
- 澄清场景、偏好、时间、工具和避讳。
- 模型输出结构化需求或课程候选，服务端验证后执行。
- 不明确的操作先澄清，避免猜测性推进。
- 为知识建立来源、使用依据、审核人、日期和版本。
- 开发草稿和试用可用内容采用明确准入规则。
- 先形成一条完整基础课程，其他风格按覆盖情况逐步开放。
- 建立检索评价样例，记录来源正确性与任务适用性。
- 模型失败时如实反馈，并保留当前步骤。

**去冗余**

合并同语义的意图规则、提示词公共约束、课程筛选和审核判断；自然语言表达不得重新实现业务状态机。

**交付与完成条件**

真实文字链路、课程包、内容审核流程和意图及检索测试。否定、提问、闲聊不会误推进；模型不能编造不存在的课程或完成动作。

专业审核未完成的内容不能进入真实试用范围。

---

### 阶段 4：语音交互与生命周期
**规格：004-voice-interaction**

**功能与工程工作**

- 按钮和起止词共享录音、识别、提交、播报状态机。
- 明确录音、转写、请求、播报、暂停状态。
- 取消、离开页面或关闭麦克风时清除未提交内容。
- 保留 120 秒单段限制，超限丢弃并说明原因。
- 普通输入在请求或播报期间不产生重复提交。
- 覆盖断连、麦克风丢失、识别失败和播报失败。
- 保留文字降级路径和读屏可感知状态。

**去冗余**

统一录音控制、订阅、计时器、回调和资源释放，避免页面维护另一套通话状态。

**交付与完成条件**

确定性音频测试及 Mac、Windows 实体设备记录；覆盖耳机、扬声器回声、背景声、暂停和重连。一次发言只产生一次业务请求；关闭后不遗留采集或监听。

合成音频测试不替代实际设备和目标用户测试。

---

### 阶段 5：受限本地视觉与授权生命周期
**规格：005-local-vision**

**功能与工程工作**

- 分别管理预览、单帧分析、持续观察和对比基线授权。
- 结果包含画面标识、时间、目标、方法、质量和不确定性。
- 模型不可用时明确降级，不冒充完整分析。
- 区分镜像预览与身体左右；方向不明的图片不输出确定左右。
- 只在光线、姿态可比时解释前后差异。
- 撤销、离开页面、结束使用后停止相应采集与分析，清理临时数据。
- 迟到结果不能重新启用已撤销能力。

**去冗余**

集中管理权限、过期规则和相机资源；真实、降级、演示结果共享必要契约，但保留来源区别。

**交付与完成条件**

受限观察实现、权限流程和异常样例验证。覆盖无人脸、多人脸、弱光、模糊、遮挡和过期画面；无授权不上传、不保留图像。

颜色变化不能被描述成妆效正确。真实妆效识别另建研究规格，明确标注、数据划分和评价方法后推进。

### 阶段 6：Full Look、标签读取与产品比较
**规格：006-styling-reading**

**功能与工程工作**

- 六个领域支持选择、跳过、编辑与确认。
- 区分已知事实、系统建议和未知信息。
- 局部修改保留其他已确认内容。
- 区分提出新风格建议与替换正在执行的教学计划。
- 图片外传前说明处理服务和用途，单独取得授权。
- 标签结果保留原始文字和不确定字符，不推测缺失成分、浓度或色号。
- 产品比较基于可追溯属性，主观偏好与客观事实分开。

**去冗余**

共享领域编辑与确认机制，但保留领域差异。供应商调用放到适配层，页面不散落供应商分支。

**交付与完成条件**

Full Look 完整流程、真实标签读取和有来源的比较。局部修改不重置其他选择；拒绝上传不产生远程请求；版本冲突可明确处理。

缺少凭证或数据时标为受阻，模拟结果不能证明真实服务通过。

### 阶段 7：确认式记忆、日志与数据管理
**规格：007-confirmed-memory**

**功能与工程工作**

- 完成课程后生成候选摘要，允许查看、朗读、修改、保存或拒绝。
- 候选内容与版本绑定，重复保存幂等。
- 摘要、日志、偏好分别授权。
- 支持只写日志，以及查看、编辑、删除和明确复用记录。
- 用户标签与审美词汇须经确认，不推断情绪或性格。
- 旧自动摘要保留来源，不直接视为用户确认内容；支持重新确认或删除。
- 删除同步覆盖派生偏好、回忆和未来模型上下文。
- 默认进度保留 30 天，已确认摘要保留 30 天；日志与偏好保留至用户删除。

**去冗余**

统一确认保存机制与数据访问边界；消除多入口直接写库、重复确认和删除后的残留副本。

**交付与完成条件**

保存交互、数据迁移与回退方案、数据库验证证据。拒绝不新增个人记忆；只保存确认版本；重复确认不重复写入；删除后不再调用；用户数据隔离。

### 阶段 8：无障碍、残余清理与交付
**规格：008-accessible-release**

**功能与工程工作**

- 汇总此前各阶段持续进行的无障碍检查。
- 完成 Mac Chrome＋VoiceOver、Windows Chrome＋NVDA 实测。
- 覆盖键盘、字号、缩放、减少动态效果、中英文和焦点顺序。
- 避免应用播报与读屏重复干扰。
- 验证目录移动、缺少模型、断网、崩溃、重启和较长会话。
- 检查麦克风、相机、事件监听与连接资源释放。
- 统一运行说明、演示说明、版本、限制和回退方法。
- 发布包排除密钥、私人数据库与媒体数据。

**去冗余**

关闭遗留兼容任务，清理已确认无用的代码、依赖、配置、资源和过时文档。必要兼容项记录真实调用方、责任人和退出条件。

**交付**

工程候选版、双平台证据、结构整改报告、已知问题、运行与回退说明。

**工程交付条件**

核心需求均有验证结论；无未解决 P0 和核心 P1；双平台完成实体检查；中断和拒绝授权仍有可用路径。

**真实试用条件**

试用课程通过专业审核，目标用户能独立控制关键任务并理解失败提示。条件不足时，保持工程候选版状态。

## 六、接口、数据与迁移要求

| 接口或数据 | 约束 |
|---|---|
| 会话命令 | 事件标识、预期步骤及必要版本校验；重试沿用事件标识 |
| 流式回复 | 区分业务已提交、生成进行中、生成失败与完整结束 |
| 前后端类型 | 由后端契约生成或校验，避免两套独立定义漂移 |
| 保存接口 | 绑定候选标识与版本，返回实际保存记录 |
| 课程结束 | 返回候选摘要，不自动写入个人记忆 |
| 视觉结果 | 标注时间、目标、方法、质量、来源及可比较性 |
| 健康检查 | 区分服务可达、依赖加载、配置具备与真实功能验证 |
| 错误响应 | 稳定错误码和可操作提示，不泄露凭证 |

兼容策略：

- 已用接口优先通过适配方式迁移。
- 旧接口不继续独立执行业务判断。
- 数据迁移有版本标识和一致性备份。
- 恢复流程验证代码与数据版本兼容。
- 清理历史实现不能破坏实际调用方或删除未经说明的用户数据。

## 七、测试、缺陷与证据管理

### 1. 追踪关系

建立：

`用户故事 → 需求 → 设计/接口 → 任务 → 测试 → 证据 → 发布版本`

出现缺陷时附加 bug 编号，关联原需求、复现测试、修复任务和回归结果。

结构整改项与产品 bug 分开记录，但可以相互关联。

### 2. 四层测试

| 层级 | 验证重点 |
|---|---|
| 业务规则 | 状态转换、幂等、确认保存、知识准入 |
| 接口与数据库集成 | 权限、持久化、迁移、竞争和错误契约 |
| 浏览器完整链路 | 页面、真实后端、刷新、取消、断连与恢复 |
| 实体设备和人工验收 | 麦克风、扬声器、相机、读屏及目标用户理解 |

每条记录标明：

- `NOT RUN`、`PASS`、`FAIL` 或 `BLOCKED`。
- 模拟或真实模型。
- 合成输入或实体设备。
- 代码、配置、数据、平台版本和运行时间。

### 3. 修复与重构顺序

1. 复现问题，或固定应保留的关键行为。
2. 确认需求和根因。
3. 迁移一个职责或一组调用方。
4. 执行相关测试。
5. 删除被替换实现。
6. 验证实际入口和完整链路。
7. 更新文档与证据。

针对竞争、取消、权限和持久化安排必要重复验证。纯搬移和低风险清理不编写只检查代码形状的测试。

### 4. 缺陷优先级

| 级别 | 示例 | 处理要求 |
|---|---|---|
| P0 | 未授权上传或保存、数据串用户、数据损坏、危险动作 | 阻断发布，优先处理 |
| P1 | 核心流程失败、错误推进、无法恢复、关键无障碍障碍 | 当前相关阶段解决 |
| P2 | 有可用替代路径的局部问题 | 安排到对应阶段并说明影响 |
| P3 | 非关键视觉或文案问题 | 主流程稳定后处理 |

状态：

`待复现 → 已确认 → 根因明确 → 修复中 → 待回归 → 已关闭／延期`

延期必须记录原因、影响、负责人和处理阶段；静态风险不直接标为已确认 bug。

## 八、去冗余专项验收

### 1. 每阶段必须回答的问题

- 同一业务规则是否已归入明确位置？
- 是否新增了需要人工同步的业务状态？
- 模块拆分是否减少职责混杂和隐式耦合？
- 是否引入循环依赖或没有必要的抽象层？
- 旧调用方是否迁移，旧实现是否按计划退出？
- 删除依据是否覆盖动态加载、运行和打包入口？
- 需求、实现与测试是否保持一致？
- 队友能否找到这项规则应在哪里修改？

### 2. 整改证据

记录以下变化：

- 同一业务规则的独立实现数量。
- 同一业务状态的独立可写来源。
- 待退出兼容项及到期情况。
- 已确认未使用代码、依赖、配置的处理结果。
- 修改代表性规则时需要同步修改的位置。
- 回归是否覆盖真实入口。

不设机械的代码缩减比例。新增少量清晰接口或测试可以增加代码量，同时降低维护成本。

### 3. 提交与评审方式

- 按单一业务主题组织改动。
- 结构调整和行为变化分成可独立审查的提交。
- 不将大范围格式化、模块搬移和业务修复混成一笔修改。
- 一个 bug 对应可验证的修复，避免夹带无关功能。
- 兼容项在所承诺阶段验收退出，不能无限延期。

## 九、团队分工、推进方式与交付包

### 1. 角色责任

| 角色 | 责任 |
|---|---|
| 产品负责人 | 确认产品意图、行为变更、优先级和阶段范围 |
| 开发负责人 | 模块设计、实现、迁移、去冗余与技术证据 |
| 测试负责人 | 复现、回归、证据整理及问题状态维护 |
| Mac／Windows 验收成员 | 实体设备与平台操作验证 |
| 专业审核者 | 审核进入真实试用的课程内容 |
| 目标用户参与者 | 验证任务可完成性、可控性和提示理解 |

一人可以兼任多个角色，但评审责任和验证来源必须明确，不将自己的实现判断自动视为独立用户验证。

### 2. 依赖与推进顺序

- 阶段 0 建立规则；阶段 1 建立可运行和可测试基线。
- 阶段 2 优先解决跨功能共用的状态问题。
- 阶段 3 建立对话与课程基础。
- 阶段 4—7 按已定义契约推进各功能，开阶段前重新确认依赖。
- 阶段 8 汇总全链路和发布验收。
- 无障碍、权限、测试和去冗余贯穿所有阶段，阶段 8 负责最终复核。

不预设缺乏依据的工期。团队确认负责人、现状和设备资源后，在任务清单中估算工作量，并将外部审核等待时间单独列出。

### 3. 每阶段交付包

每阶段提交七项：

1. 规格、技术方案、任务及评审记录。
2. 可运行版本和版本标识。
3. 测试结论与可检查证据。
4. 已修复、未解决和受阻的问题。
5. 去冗余记录：合并、删除、暂留及理由。
6. 接口和数据影响、迁移与回退说明。
7. 队友可执行的简短验收步骤。

### 4. 阶段完成判断

只有以下问题均有明确结论，才能宣布阶段完成：

- 本阶段承诺的用户行为是否实现？
- 每项验收条件是否有验证结果？
- 是否引入跨模块回归？
- 去冗余和旧实现退出任务是否完成？
- 剩余依赖、风险和限制是否如实记录？
- 当前版本能否作为下一阶段的稳定基础？
- 能否回退到上一个可用版本？

最终交付应让队友和老师能够沿着一条清晰路径检查：

> 为什么需要这个功能 → 规格如何定义 → 代码由谁负责 → 如何验证 → 出错后如何定位 → 修复后如何防止再次发生。
